1. Écoinformatique (slides 9-29)

Chaque octet se matérialise dans le monde réel : consommation d'énergie, de ressources physiques (métaux, silice, eau), émissions de gaz à effet de serre (eGES) et déchets. Matériel et logiciel ont un cycle de vie qui impacte l'environnement de leur création à leur destruction. Phénomène d'obésiciel (logiciel obèse).

Empreinte carbone du numérique mondial≈ 4 % des eGES = ×1,5 l'aérien mondial (GIEC 2022)

Définition · jour de dépassement

Jour de l'année à partir duquel toutes les ressources naturelles renouvelables en 1 an ont été consommées. J = (B / E) × 365, B = biocapacité, E = empreinte écologique, tous deux en hectares globaux.
Monde 2026 : 30 juillet · France 2026 : 24 avril (2023 : 5 mai). Conso : 170 % du rythme mondial (≈ 1,7 planète), 300 % au rythme français. Qatar le plus tôt (6 fév. 2025), Uruguay le plus tard (17 déc.).

Limites planétaires

9 limites : climat · biosphère · azote et phosphore · usage des sols · eau douce · acidification des océans · ozone · aérosols · nouvelles entités. 6/9 dépassées en 2023, 7/9 en 2026 ; la plus récente : l'acidification des océans (2025). Cause n°1 côté numérique : l'obsolescence par obésité logicielle.

Équipements (Arcep/ADEME) : plus de 800 M d'équipements en France (2020), dont 245 M d'objets connectés ; smartphones ≈ 14 %, téléviseurs ≈ 13,7 %, datacenters + réseaux ≈ 21,6 %. Scénarios 2050 : Génération frugale ÷2 (le seul qui baisse) · Coopérations territoriales ×1,6 · Technologies vertes ×5 · Pari réparateur ×14. Web (GreenIT) : 1 500 Mt éq. CO₂/an ; par Européen, 39 % du budget GES soutenable.

L'écoconception

Écoconcevoir un service en ligne, c'est, à niveau de qualité constant, réduire la quantité de moyens informatiques nécessaires (son empreinte matérielle), à chaque étape du cycle de vie. 4 leviers : type de terminal, durée de vie du terminal, temps passé, type de connexion. Le gros des économies vient de l'allongement de la durée de vie des équipements ; la conception en amont pèse plus que l'optimisation des lignes de code.

Simplicité (qualitative) : chaque besoin couvert par un ensemble cohérent de fonctionnalités, une interface homogène. Frugalité (quantitative) : couverture et profondeur fonctionnelles au strict minimum.

Piège QCM

Pertinence = utilité × rapidité × accessibilité : un produit, pas une somme. Un facteur faible ⇒ l'utilisateur change de service ⇒ 100 % d'impacts inutiles.

2. Analyse des exigences (slides 30-52)

Exigences logicielles : description des propriétés et fonctionnalités du système cible, reflet des besoins de l'utilisateur. Ingénierie des exigences (IE) : collecter, analyser, puis présenter les exigences dans la SRS (System Requirements Specification). Référence : Sommerville.

FonctionnellesNon-fonctionnelles
Services que le système doit fournir, comment il réagit à des entrées, comment il se comporte dans certaines situations. Utilisateur = énoncés de haut niveau ; système = services décrits dans le détail. Contraintes sur les services : propriétés (fiabilité, temps de réponse, stockage), contraintes (E/S, représentations), processus (AGL, langage, méthode). Peuvent être plus critiques : non satisfaites ⇒ système inutile.

BIBSYS : « visionneuses adaptées » est ambigu (une par type de document ? une seule visionneuse texte ?). Une exigence ambiguë est interprétée différemment. Complètes = couvrent tout ; consistantes = sans contradiction ; les deux à la fois : impossible en pratique.

PropriétéMesures
Vitessetransactions/s, temps de réponse, rafraîchissement écran
TailleMo, nombre de puces ROM

Piège QCM

Fiabilité = avant l'échec (temps moyen, disponibilité). Robustesse = après l'échec (redémarrage, corruption).

Processus d'ingénierie des exigences

Démarre si l'étude de faisabilité est concluante. 4 activités génériques : élicitation · analyse · validation · gestion. Éliciter ≈ recueillir, découvrir, avec les parties prenantes (stakeholders : pour un DAB, clients, managers, guichet, sécurité, maintenance, régulateurs…). Cycle d'élicitation-analyse : 1. découverte → 2. classification & organisation → 3. priorisation & négociation → 4. spécification.

Cas d'utilisation et scénarios

Technique à base de scénarios en UML qui identifie les acteurs (personne ou composant à l'origine d'une interaction) et décrit l'interaction. Un cas d'utilisation = objectif du système motivé par le besoin d'un ou plusieurs acteurs. Diagramme : package (rectangle = le système), acteurs (bonshommes), cas (ellipses), associations (traits), notes (coin corné).

Définition · scénario (5 éléments)

1. situation de départ · 2. flux normal · 3. ce qui peut mal se passer · 4. activités parallèles · 5. état final.

Diagramme de séquence

Participants « objet : Classe » soulignés, ligne de vie verticale pointillée, appel = flèche pleine, retour = flèche pointillée, exécution = barre d'activation. Un message reçu par un objet devient une méthode de sa classe. Modélisations de système (§8.4) : contextuelles, comportementales, orientées données, orientées objet.

Contrôle d'accès : clavier 4 chiffres, voyants rouge/vert (multiplicité 2), minuteur 5 s / 20 s, porte, alarme, base de codes. saisirChiffre → chiffreSaisi → verifierCode → deverrouiller → ouvrir. Pas de message entre deux acteurs.

3. Modélisation objet & UML (slides 52-61)

Les modèles objet décrivent le système en classes (abstraction d'objets aux attributs et services communs) et associations. Ils reflètent naturellement le monde réel ; les entités abstraites sont plus difficiles. Identifier les classes est difficile et demande une connaissance profonde du domaine ; les classes du domaine sont réutilisables.

Héritage : hiérarchies où le sommet porte les propriétés communes. Héritage multiple : 2 risques, conflits sémantiques (même nom, sens différent) et réorganisation plus complexe. Java l'interdit pour les classes : une classe implémente plusieurs interfaces. Agrégation : classes-collections composées d'autres classes (losange côté ensemble). Modèle comportemental : diagrammes de séquence ou de collaboration.

Piège QCM

En UML standard, généralisation = héritage = trait plein ; la flèche pointillée s'appelle réalisation. Retiens : plein = extends, pointillé = implements.

5. Complexité algorithmique (slides 62-76)

« Ce qui ne se mesure pas ne s'améliore pas. » Exemple du trafic aérien : distances entre toutes les paires d'avions, deux boucles imbriquées, n(n−1) calculs ⇒ O(n²). Mesures : 4 000 → 190 ms, 8 000 → 664 ms, 16 000 → 2 647 ms : taille ×2 ⇒ temps ×4.

Définition · Grand O

Une abstraction de la performance, indépendante du matériel et du langage ; pas une mesure en unité de temps ; un ordre de grandeur du nombre de calculs élémentaires ; une limite asymptotique, 3 cas : favorable (limite basse), pire (limite haute), moyen ; seulement pour un très grand nombre d'entrées.

Pourquoi pas chronométrer ? Dépendance au matériel, à la mémoire occupée, chargement de la JVM, comparaison et prédiction difficiles.

Grand ONomReconnaître
O(1)constanteaccès direct
O(log n)logarithmiqueentrée divisée par 2 à chaque étape (recherche binaire)
O(n)linéaireune passe (countChars, recherche linéaire : n/2 tours en moyenne)
O(n log n)log-linéairebons tris (quicksort moyen)
O(n²) / O(n³)quadratique / cubique2 / 3 boucles imbriquées (intersection naïve)
O(2ⁿ) / O(n!)exponentielle / factoriellevoyageur de commerce, force brute, factorisation

Piège QCM

Quand n double : O(n) ×2 · O(n²) ×4 · O(n³) ×8 · O(log n) +1 étape · O(n log n) un peu plus que ×2. On garde le terme dominant : 3n² + 5n + 2 ⇒ O(n²) ; n/2 ⇒ O(n). La cryptographie repose sur l'absence d'algorithme polynomial connu de factorisation.

Dans ton TP

TP6 : System.nanoTime() avant/après, ÷ 1 000 000 pour des ms (sert à mesurer une durée, pas l'heure). Taille ×10 ⇒ temps un peu plus que ×10 ⇒ n log n. Petites tailles peu fiables (JVM pas encore « chauffée »).

6. Structures de données (slides 77-106)

Structure de données abstraite (TAD) : ce que la structure doit faire, pas comment. Tableaux, structures chaînées (listes, arbres, graphes), piles LIFO, files FIFO, tables associatives.

Liste simplement chaînée

Nœuds (élément + next) dans un ordre linéaire ; tête, queue ; queue.next == null ; taille indéfinie ; position non indexée. Insertion en tête : v.next = head; head = v; size++ (O(1)). Insertion en queue : v.setNext(null); tail.setNext(v); tail = v. Suppression en tête : head = head.getNext(). Suppression en queue : parcours pour trouver l'avant-dernier, O(n). Toujours se demander « et si la liste est vide ? ».

Liste doublement chaînée & sentinelles

Chaque DNode a next et prev. Sentinelles header/trailer : nœuds factices sans élément (header.prev == null, trailer.next == null, non comptés dans size) qui simplifient la programmation (plus de cas particuliers). Insertion de v entre u et w : 4 pointeurs (u.next, v.prev, v.next, w.prev). Suppression : on court-circuite (prev.next = next, next.prev = prev).

private void addAfter(DNode u, String e) {      // ton TP
  DNode w = u.getNext();
  DNode v = new DNode(e, u, w);
  u.setNext(v); w.setPrev(v); size++;
}

Arbres et parcours

Structure hiérarchique, racine en haut ; frères = même parent ; externe = feuille (aucun enfant), interne = au moins un enfant. Formel : racine sans parent, tout autre nœud a un parent unique. Récursif : un arbre est vide ou une racine + des sous-arbres ⇒ il peut être vide. TAD : element(), root(), parent(v), children(v).

Infixe d'un arbre binaire de recherche ⇒ ordre croissant. Exemple du cours (postfixe) : 10 → (20, 30 → (40, 50)) donne 20 40 50 30 10.

Tables associatives et hachage

Map : paires (clé, valeur), clés uniques, valeurs répétables. Avec une liste : chaque opération en O(n). Table de hachage = tableau d'alvéoles + fonction de hachage : valeurs indexées par la valeur de hachage (pas par la clé), O(1) en moyenne, risque de collision (2 clés distinctes, même valeur). En Java, 2 temps : hashCode puis compression modulo N. Bonne fonction = uniformité + rapidité + taille. Taille première (évite les diviseurs communs) ou puissance de 2 (modulo par décalages).

7. Algorithmes de tri (slides 107-118)

Intersection naïve de 2 tableaux : O(n²). En triant (O(n log n)) : trier un tableau + recherche binaire pour chaque valeur ⇒ O(n log n) ; ou trier les deux + deux pointeurs ⇒ 2·n log n + n = O(n log n). Un tri ne peut pas être efficace dans toutes les situations (aléatoires, presque triées, inversées, doublons).

Tri à bulles : plusieurs passages en intervertissant les voisins mal ordonnés ; le plus grand « remonte » à la fin. Simple mais O(n²). Exemple : 5 1 4 2 → 1 4 2 5 → 1 2 4 5.

Récursivité & divide-and-conquer

Récursivité : une fonction s'appelle jusqu'à la condition d'arrêt ; contient une ou plusieurs conditions d'arrêt + un ou plusieurs appels récursifs. Récursivité ≠ récurrence. Patron : Divide (sous le seuil, résoudre ; sinon découper) · Conquer (résoudre récursivement) · Combine (fusionner).
binarySearch(x, array, start, end)          // tableau TRIÉ, O(log n)
  if (start <= end) then
    mid <- (end - start)/2 + start           // évite le débordement de (start+end)/2
    if (array[mid] = x) then return true      // arrêt 1 : trouvé
    if (array[mid] > x) then return binarySearch(x, array, start, mid - 1)
    return binarySearch(x, array, mid + 1, end)
  return false                                // arrêt 2 : start > end

Quicksort

Algorithme de Tony Hoare, récursif, divide-and-conquer. Lomuto : pivot = dernier ; on cherche le 1er élément supérieur au pivot, on l'échange avec chaque élément inférieur rencontré ensuite, puis le 1er supérieur avec le pivot ⇒ L (gauche) et G (droite). Tri en place.

int partition(ArrayList<Integer> s, int debut, int fin) {   // ton TP6
  Integer pivot = s.get(fin);
  int a = debut;
  while (a < fin && s.get(a) <= pivot) a++;
  for (int b = a + 1; b < fin; b++)
    if (s.get(b) < pivot) { swap(s, a, b); a++; }
  swap(s, a, fin);                 // pivot à sa place
  return a;
}

Complexité du quicksort

Meilleur et moyen : O(n log n). Pire : O(n²), quand le pivot est toujours le min ou le max (pivot = dernier sur une liste déjà triée ou inversée : une partition vide à chaque appel) ⇒ récursion de profondeur n ⇒ StackOverflowError dès 50 000 éléments dans ton TP. Remèdes : pivot aléatoire, médiane-de-trois (heuristique : vite et assez bon, sans garantie), médiane-de-9 (meilleur pivot, plus lent).

TP2 · Listes chaînéesStructures sans sentinelles. SinglyListClass récursive d'Integer : size, isEmpty, first, last, addFirst, addLast, removeFirst. Sur liste vide : retourner null sans modifier. private static class Node imbriquée. Puis liste double, equals(), comptage d'une liste circulaire, MyLinkedList<T> implements List<T> testée avec les 10 meilleurs scores.Sans static, Node serait une classe interne liée à une instance de la liste (référence cachée). Avant-dernier : avancer tant que cur.next.next != null, O(n). Inverser en espace O(1) sans récursivité : 3 pointeurs prev / cur / next. Liste circulaire : compter jusqu'à revenir au nœud de départ. Milieu sans compteur : deux pointeurs (tête + queue qui se rejoignent, ou lent + rapide). Concaténer 2 listes à sentinelles : O(1).
TP4 · Arbres et pilesArbre binaire générique (sur le modèle de SinglyListClass), parcours, toString() préfixe, test « (5 + 2) * 8 ». Arbre n-aire testé sur le DOM d'une page HTML. Pile MaPile<T> sur une structure chaînée. Évaluation de la NPI.Préfixe = commence par la racine ; infixe impossible en n-aire. (2 + 3) * 5 − (9 − (1 + (3 + 4)) * 3) ⇒ postfixe 2 3 + 5 * 9 1 3 4 + + 3 * − − = 40. ((5 + 2) * (8 − 3)) / 4 ⇒ 5 2 + 8 3 − * 4 /. Algorithme : opérande ⇒ empiler ; opérateur ⇒ y ← dépiler, x ← dépiler, empiler x op y.
TP6 · TrisTri à bulles du CM (écrit pour un tableau) adapté à une liste doublement chaînée. Quicksort sur ArrayList<> après un déroulé pas à pas de la partition. Passage à l'échelle : randomInit(Integer[] input, int size), mesures avec System.nanoTime(), relevés en CSV.nanoTime = nanosecondes, par différence (÷ 10⁶ ⇒ ms). Pire cas du quicksort : O(n²). Randomisé : position du pivot tirée au hasard, le reste inchangé. Médiane-de-trois (tête, milieu, queue) : {27, 4, 15} ⇒ 15 ; c'est une heuristique (rapide, assez bonne, sans garantie), généralisable à plus de 3 valeurs. Bulles sur liste : échanger les éléments, pas les nœuds.
TP8 · Collections et MapsChoisir la collection la plus adaptée et apprendre à se documenter (javadoc, tutoriel Oracle, Guava). Compétition : Participant, Amateur (score, non classés), Competiteur (classés par score). Annuaire : numéro (long) indexé par nom.Amateurs ⇒ HashSet (ou List). Compétiteurs toujours triés ⇒ TreeSet + Competiteur implements Comparable<Competiteur> (ou Comparator). Piège : même score ⇒ compareTo = 0 ⇒ le TreeSet n'ajoute pas le second, il faut départager. Annuaire ⇒ Map<String, Long> : HashMap O(1) en moyenne, TreeMap pour l'ordre alphabétique en O(log n).

TD1-2 · Impôts locaux d'une mairie (héritage)

class Home {                          // owner, address, surface
    public double tax() { return 2 * surface; }          // 2 €/m²
}
class PersonalHome extends Home {     // + roomNb, pool
    @Override public double tax() { return super.tax() + 15 * roomNb + (pool ? 80 : 0); }
}
class ProHome extends Home {          // + employeeNb
    @Override public double tax() { return super.tax() + 150 * (employeeNb / 10); }
}

Deux généralisations vers Home (trait plein ▷). for (Home h : homes) h.tax() appelle la version de la classe réelle (liaison dynamique). « 150 € par dizaine d'employés » : la division entière ci-dessus arrondit à la dizaine inférieure ; vérifie la convention de ton groupe.
